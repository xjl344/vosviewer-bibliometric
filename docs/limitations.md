# 已知限制

本文档诚实列出本工具的局限。**请在使用前阅读，避免误用导致结论错误。**

---

## 一、VOSviewer 相关

### 窗口会弹出，无法避免

VOSviewer 是 Swing GUI 程序，**没有无头模式**。每次导出图片都必须启动一个窗口，
且它出图后不会自动退出——本工具的处理方式是「启动 → 轮询等目标文件出现 → 关闭进程」。

**这不是错误，是设计限制。** 已优化到最少：

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 3 视图 + SVG | 7 次启动 | **3 次** |

优化依据（实测）：
- 一次启动可同时导出多种格式（`-save_screenshot_png a.png -save_screenshot_svg a.svg`）
- 「算布局聚类」与「出图」可在同一次启动内完成（VOSviewer 会先算完布局再截图）
- **但多个视图无法在一次启动内完成**（视图参数互斥，只有最后一个生效）

### 布局由 VOSviewer 决定，本工具不干预

本工具调用 VOSviewer 的布局与聚类算法（`-run_layout -run_clustering`），
而不是自己实现。原因：VOSviewer 的算法是学术界的参考实现，用它算出的结果
**可被审稿人接受、可复现**。

本工具自带的 Louvain 实现只在两种情况下使用：
1. 生成报告指标（因为需要拿到聚类结果做后续计算）
2. VOSviewer 不可用时的降级方案

**注意**：两者结果可能不同（本工具报告的聚类数来自 VOSviewer 回写的结果）。

### 图形外观可能需要手工微调

当网络较松散（存在少数远距离节点）时，自动布局可能呈现横向拉伸。
这不影响分析结论，但如需更紧凑的图，可以：

1. 把 `vosviewer_input/map.txt` 与 `network.txt` 拖进 VOSviewer 界面手工调整
2. 加 `--largest-component` 去掉孤立节点
3. 加 `--min-line-strength` 隐藏弱连线

## 二、数据源限制

### OpenAlex 的 keywords 不适用于本分析

**这是最容易踩的坑。** OpenAlex 的 `keywords` 字段是**算法抽取的概念**，
不是作者标注的关键词，会混入两类噪声：

1. **学科标签**：`Computer science`、`Medicine`、`Gerontology`、`Marketing`
2. **概念片段**：`Service (business)`、`Context (archaeology)`、`Work (physics)`

实测 350 篇文献抽出 728 个「关键词」，56% 只出现一次，聚类结果中出现**纯垃圾簇**：

> 聚类 = `Process (computing)` | `Field (mathematics)` | `Set (abstract data type)` | `Work (physics)` | `Quality (philosophy)`

这些词彼此毫无主题关系，只因为被分配到重叠的论文里。

**正确用途**：OpenAlex 适合**文献检索与获取**（用 `fetch_openalex.py`），
不适合直接当关键词来源。

### 各数据源的关键词质量对照

| 数据源 | 关键词性质 | 能否用于共现分析 |
|---|---|---|
| WoS 的 `DE` | 作者亲自标注 | ✅ 首选 |
| CNKI 的 `K1` / `%K` | 作者亲自标注 | ✅ 首选 |
| Scopus 的 Author Keywords | 作者亲自标注 | ✅ 可用 |
| PubMed 的 KeywordList | 作者亲自标注 | ✅ 可用 |
| PubMed 的 MeSH | 人工标引 | ✅ 可用 |
| WoS 的 `ID`（Keywords Plus） | 算法生成 | ⚠️ 可用但需说明 |
| Scopus 的 Index Keywords | 算法生成 | ⚠️ 同上 |
| **OpenAlex 的 keywords** | **算法抽取概念** | ❌ **不适用** |

## 三、指标解读陷阱

### 陷阱 1：把「0 篇命中」当成「无相关研究」

**检索命中量只能说明「关键词是否共现」，不能说明「研究是否做过」。**

不同研究者对同一研究可能用完全不同的关键词。实测案例：某次「主动健康 × 独居老人 ×
智能家居」三者交叉检索命中 **0 篇**，但人工核查邻近领域后发现了一篇
**2026 年发表的高度相关论文**（覆盖老年人 + 智能家居 + 主动健康，仅缺「独居」限定）。

**正确做法**：
1. 检索命中量只作为线索
2. **必须人工核查邻近领域的论文**
3. 表述用「现有研究多聚焦于 X，尚未针对 Y」而非「尚无研究」

### 陷阱 2：把「统计显著」当成「有学理意义」

统计检验只能说明「这个低共现不太可能是随机波动」，
**不能说明「这两个词属于同一个研究领域」**。

实测案例：120 篇数据里「智慧养老 × 智能家居」零共现，超几何检验 **p = 0.023，显著**。
但一查标题就露馅——「智能家居」那 18 篇里大部分**根本不是养老研究**：

- 基于物联网的节能型**船舶**智能家居系统设计
- 智能家居环境下**住宅装修材料**性能优化研究
- 面向智能家居的**低功耗无线通信协议**设计

**「零共现」不是学术断层，而是检索污染造成的假象。**

**正确做法**：报告研究空白前，先人工抽读 10–20 条标题确认聚类成员真的属于同一领域。

### 陷阱 3：用 Q 值高低判断分析好坏

模块度 Q 是聚类「干净程度」的指标，但：

- **Q 低不等于分析失败**。高度交叉的领域 Q 天然偏低（实测 0.05–0.15），
  但聚类主题可能很清晰。关键看「Q 低时聚类成员是否同质」
- **合并同义词会让 Q 下降，但这是正确的**。重复概念（如「老年人」与「老年群体」）
  作为独立节点存在时会人为撑高 Q。实测某语料合并后 Q 从 0.5406 降到 0.4339，
  但合并后的结果才是真实的

**实测 Q 值分布**：

| 数据 | Q | 说明 |
|---|---|---|
| 120 篇（检索污染 38%） | 0.386 | 表面正常，但结论不可用 |
| 248 篇（含枢纽词） | 0.338 | 星形结构，主题被压平 |
| 248 篇（剔除枢纽词） | 0.484 | 结构清晰浮现 |
| 320 篇（OpenAlex 概念词） | 0.099 | 数据源不当 |

### 陷阱 4：忽略枢纽词

**检索词本身往往出现在半数以上文献中**，会形成星形枢纽把真实结构压平。

实测：248 篇「主动健康」文献中该词出现 124 次（50%）。
- 不剔除：4 个聚类，Q = 0.338，图呈放射状细线
- 剔除后：7 个聚类，**Q = 0.484**

判断标准：最高频词占文献总数 **> 40%** 时强烈建议剔除。

## 四、样本量限制

| 文献量 | 可用性 |
|---|---|
| < 50 篇 | 不建议做计量分析，聚类不稳定 |
| 50 – 100 篇 | 勉强可用，结论需定位为探索性 |
| **100 – 500 篇** | **推荐区间** |
| > 500 篇 | 可用，但需提高 `--min-occurrences` 避免图过密 |

样本量不足时统计功效不足，**可能漏掉真实的研究空白**（是漏报，不是误报）。
工具会在文献量 < 50 篇时主动提示。

### 小网络需要调整分辨率

节点数 < 40 时，默认 `resolution=1.0` 会导致聚类碎片化
（实测 28 个节点跑出 9 个聚类，平均每簇 3 个节点，无解读价值）。
**建议降到 0.6–0.8。**

## 五、同义词归并的局限

### 共现率信号对低频词较弱

工具用「共现率」区分真同义词与相关概念：
- 共现率低 → 很可能是同义写法（作者会选其中一个）
- 共现率高 → 很可能是不同概念（作者会同时用）

**但对出现 2–3 次的低频词，这个信号不可靠**——低频词不共现是常态，
不一定是同义词。这类候选需结合语感判断。

### 包含关系检测有误报

中文靠加修饰词造新词，所以工具会检测包含关系（如「青少年」⊂「儿童青少年」）。
但也会误报，例如「条件风险感知」⊂「无条件风险感知」——**两者意思相反**。

工具已用共现率排序把这类误报排到末尾（实测那对的共现率是 1.00），
但**最终仍需人工确认**。

## 六、术语与跨语言限制

**中英文检索结果不能直接类比。**

例如「主动健康」是中国的政策概念（源自《「健康中国 2030」规划纲要》），
英文 `proactive health` 并不是一个同等明确的政策术语，
因此在英文文献中的命中量可能被低估。

做中英文对比时，应说明术语对应关系，不要把「英文命中少」
直接解释为「国际研究少」。

## 七、未验证的部分

诚实说明以下内容**尚未经过充分测试**：

- 超大语料（> 5000 篇）的性能表现
- WoS 的「作者/机构/国家」共现分析（本工具目前只做关键词共现）
- 共被引分析与文献耦合分析
- **Linux / macOS 上的完整出图链路**——解析层已在三平台 CI 上验证，
  平台检测与执行权限处理已实现，但 Java + VOSviewer 的调用
  **只在 Windows 上实测过**

### 跨平台实现说明

虽然完整链路未实测，但已知的平台差异都已处理：

| 差异 | 处理 |
|---|---|
| Java 包按平台不同 | `detect_java_platform()` 按 `platform.system()` + `machine()` 自动选包 |
| zip 不保留 Unix 权限位 | 解压后调 `_make_executable()` 补 `+x` |
| Linux 包是 tar.gz 而非 zip | 按 URL 扩展名选解压方式，两种都支持 |
| 结束进程的方式不同 | 优先 `terminate()`/`kill()`（跨平台），Windows 额外兜底 `taskkill` |
| 路径分隔符 | 全部用 `os.path.join`，无硬编码分隔符 |

如果你在 Linux 或 macOS 上跑通了，欢迎提交 issue 或 PR 补充验证结果。
